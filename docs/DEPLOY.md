# Deploying Lodestar on Render, with Neon and Qdrant Cloud

This puts Lodestar on the internet with three free tiers:

| Piece | Service | What it holds |
|---|---|---|
| The app | [Render](https://render.com) web service, from the root `Dockerfile` | The API under `/api` and the built frontend everywhere else |
| Postgres | [Neon](https://neon.tech) | Profiles, answers, events, documents, the agent's checkpoints |
| Memory search | [Qdrant Cloud](https://cloud.qdrant.io) | The student's own document passages, memory notes, coaching tips |

Local development doesn't change: `make up` still runs everything in Docker.

## 1. Neon (Postgres)

1. Create a project. Any region works; pick the one closest to your Render region.
2. In **Connection details**, turn **Connection pooling off** and copy the connection string. It
   looks like `postgresql://neondb_owner:…@ep-…-….eu-central-1.aws.neon.tech/neondb?sslmode=require`.
   - Use the direct host, not the `-pooler` one. The LangGraph checkpointer uses prepared
     statements, which a transaction pooler doesn't keep between queries.
   - Keep `?sslmode=require`.
3. Nothing else to do. On its first start the app runs the migrations (`alembic upgrade head`),
   which create the schemas, the row-level security policies and the three database roles. The
   Neon owner role is allowed to create roles, so this works as it does locally.

Neon suspends an idle database after a few minutes; the first request after that takes a second
or two longer while it wakes. The connection pool checks connections before using them.

## 2. Qdrant Cloud (memory search)

1. Create a free cluster.
2. Copy its URL and create an **API key** for it. Write the URL with port 443:
   `https://…cloud.qdrant.io:443`. Qdrant Cloud serves the same API on 443 and 6333, and some
   networks block 6333 (a connection timeout in the logs means that).
3. The app creates its collections on the first start. If Qdrant can't be reached, the app still
   runs, without document search or memory (sessions keep working, answers come from the course
   notes alone).

## 3. Render (the app)

1. Push the repository to GitHub.
2. In Render: **New → Blueprint**, pick the repository. Render reads `render.yaml` and creates one
   web service, `lodestar`.
3. Fill in the values Render asks for:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The Neon connection string from step 1 |
| `QDRANT_URL` | The Qdrant cluster URL from step 2, ending in `:443` |
| `QDRANT_API_KEY` | The Qdrant API key |
| `LODESTAR_OPERATOR_LLM_PROVIDER` | Optional, for example `gemini` (see below) |
| `LODESTAR_OPERATOR_LLM_KEY` | Optional: that provider's API key |
| `LODESTAR_OPERATOR_LLM_MODEL` | Optional, for example `gemini-3.5-flash-lite` |

   `LODESTAR_MASTER_KEY` is generated by Render (it encrypts students' own API keys; don't change
   it afterwards, or saved keys can't be read). `LODESTAR_DEMO=1` keeps the "Demo person" button.

4. Deploy. The first build takes a while: it builds the frontend and bakes the embedding and
   speech models into the image, so nothing is downloaded while a student waits. When the health
   check (`/api/health`) passes, open the service URL and press **Look around as Alex**: the demo
   person is created on the first press, with a classmate group for the class view.

### Which model writes the replies

Render has no Ollama, so there are three cases:

- **No model configured**: replies are built from fixed templates over the same facts, in English,
  French and Derja. Everything works; the replies are plainer.
- **`LODESTAR_OPERATOR_LLM_*` set**: students who switch **Cloud AI** on (Settings → Privacy) get
  replies written by that model, in their language, checked by the same verifier. Their name is
  removed before anything is sent. Students who leave Cloud AI off keep the templates.
- **A student adds their own key** in Settings → AI provider: that key is used first.

### Memory and plan size

The server uses about 500-600 MB once the embedding models are loaded. Render's Free and Starter
instances stop at 512 MB, so under load Render may restart the service for memory. For a demo
that is usually fine; for anything longer, choose the Standard plan in `render.yaml`.

Lodestar's own notes about a student (`LODESTAR_MEMORY_DIR`) are files on the instance's disk,
which Render clears on every deploy. Everything else lives in Neon and Qdrant and survives.

## Languages

The interface is in English, French and Tunisian Arabic (Derja). The browser picks one from its
language settings; a link can force one with `?lang=fr` or `?lang=tn`, and the choice is kept in
the browser. In Derja the course stays in French, the way it is taught in Tunisia.

## Checking a deployment

- `https://<service>.onrender.com/api/health` returns `{"status": "ok"}`.
- `https://<service>.onrender.com/?lang=fr` opens the app in French.
- Render's logs show `Qdrant unavailable; memory is off for this run` if the Qdrant URL or key is
  wrong, and a migration error if the Neon string is wrong.
